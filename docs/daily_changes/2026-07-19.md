# 2026-07-19

## V46 종료 확인

- v46 학습은 4425회 부근에서 종료했다. GUI 비교에는 파지·들기·수평 운반과 성공률의 균형이
  좋았던 `model_2775.pt`를 사용했다. 사용자는 이 체크포인트의 파지, 안전 상승과 수평 운반은
  양호하지만 중앙 정렬 뒤 목표 높이까지 내려가는 동작이 지나치게 느리다고 확인했다.
- 최근 50회 기준 v45 2800회의 중앙 정렬 진입률과 중앙 정렬 뒤 놓기 카운터는
  `.75731/74.61`이었다. 조건부 시간은 약 `98.52 control`이다. v46 2800회는
  `.76049/75.82`, 조건부 약 `99.70 control`로 줄지 않았다.
- v46의 하강 목표 보간은 하강 진입당 약 `11.79/12 control`까지 진행됐다. 추종·안정성 때문에
  멈춘 구간도 합계 약 `12.49 control`이므로 12단계 보간을 줄이는 것만으로 약 100단계의 조건부
  지연을 설명할 수 없다.
- Z 우선 위치 이득을 `.16 -> .20`으로 올린 결과, DLS 뒤 관절 목표의 수직 이동 누계는
  `.03094 -> .03429m`로 늘었지만 실제 큐브의 목표 방향 수직 진행은 `.03319 -> .03314m`로
  사실상 같았다. 더 큰 이득은 목표 backlog만 밀 뿐 실제 수렴 병목을 없애지 못했다.

## V47 목표 선행량 대체 경로

- 기존 3단계 목표 선행량을 첫 후보로 유지한다. 이 후보가 모든 직교 좌표계·회전·관절·연속성
  검사를 통과하면 제어 결과는 이전과 완전히 같다.
- 3단계 후보가 거절됐을 때 기존 코드는 이전 관절 목표를 진행 조건 없이 안정화 후보로 먼저
  받아들였다. 이 후보가 유효하면 현재 오차에서 다시 계산한 1단계 진행 후보는 검사하지 않았다.
  안전하지만 현재 Z 오차를 줄이지 않는 목표가 반복 선택될 수 있는 구조였다.
- v47은 중앙 정렬 뒤 실제 Z 명령이 있는 구간에서만 1단계 후보도 함께 검사한다. 두 후보가 모두
  안전하면 현재 Z 주축 진행률이 엄격히 더 큰 경우에만 1단계 후보로 바꾼다. 진행률이 같거나 낮고,
  값이 유한하지 않거나, 후보가 안전 검사를 하나라도 통과하지 못하면 기존 안정화 목표를 유지한다.
- 중앙 정렬 전 XY 구간은 기존 우선순위를 그대로 쓴다. 3단계 선행량, 최대 하강량
  `3mm/control`, 가속도·저크, DLS 감쇠, 목표 연속성, 관절 한계, 미끄러짐과 충돌 검사도 바꾸지
  않았다. 놓기 목표 `.670m`, 높이 허용오차 위 `2mm`·아래 `3mm`, 최대 속도 `.06m/s`와 성공
  조건도 그대로다.
- 웹 ChatGPT Pro의 전체 제어 경로 반론 검토에서도 같은 우선순위 역전을 가장 작은 v47 수정
  대상으로 판단했다. 다만 모든 후보가 무효인 안전 정지가 더 큰 원인일 가능성은 현재 전 구간
  카운터만으로 배제할 수 없다는 지적도 반영했다.
- TensorBoard에 Z 우선 구간 전용 `better_incremental_opportunities`, `progress_upgrades`,
  `previous_stabilizations`, `hard_holds`, `increment_invalid` 5개 lead 진단값을 추가했다. 첫 값이
  0이면 새 경로가 실제 궤적에 개입할 기회가 없던 것이고, 마지막 두 값이 지배적이면 다음 원인은
  후보 순서가 아니라 DLS·관절 한계 때문에 유효한 1단계 후보 자체를 만들지 못한 것이다.
- 전체 회귀 테스트 `137개`, Python 컴파일과 `git diff --check`를 통과했다. Isaac 학습이나
  물리 시뮬레이션은 새로 실행하지 않았다.

처음부터 실행하는 명령:

```bash
python scripts/rsl_rl/train.py --task=Isaac-PickPlace-OpenArm-TestUSD-Bi-Stage-v0 --num_envs=5120 --headless --device=cuda --max_iterations=5000 --run_name=fresh_z_progress_lead_v47
```

첫 비교는 2500~3000회에서 한다. 최근 50회 파지·들기·검증 운반은 각각 v46보다 `1%p` 넘게
떨어지지 않고 최소 `94%`를 유지해야 한다. `task_phase_center_to_release_steps /
task_place_centered`는 v46의 `99.70 control`보다 최소 `15%` 줄어 `84.7 control` 이하여야 하며,
중앙 정렬 뒤 시간 초과도 v46의 `19.69%`보다 낮아야 한다. 더 나은 1단계 후보 기회가 실제 적용으로
이어지고 물리 Z 진행이 늘어야 원인과 결과가 맞는다. 기회가 드문데 `increment_invalid`와
`hard_holds`가 지배적이면 이 수정은 실제 결함이지만 주된 병목은 아니라고 판정한다. 미끄러짐 감시,
목표 높이 오차, 놓기 속도나 바스켓 접촉이 늘면 빠르더라도 채택하지 않는다.

## V47 종료와 V48 운반 높이 보완

- v47은 5000회까지 완료했다. `model_4999.pt` 최근 50회 파지·들기·운반·성공은
  `89.76/89.43/89.41/60.11%`였지만 GUI에서 운반 중 바스켓에 살짝 닿는 경로가 확인됐다.
  접촉 센서가 없어 큐브·손가락·링크 중 접촉 주체는 아직 모른다.
- 들기 성공당 바스켓 근처 저고도 제어 주기는 2500회 `1.48`에서 4999회 `67.53`으로 후기 학습에서
  크게 늘었다. 기존 들기 전 안쪽 진행은 같은 구간 `.0197m -> .0090m`로 줄었으므로, 기존 비용이
  보지 못하는 후기 저고도 체류가 유력하다. 이를 직접 확인하도록 들기 완료 전후 지표를 나눴다.
- 수평 운반 보상은 현재 높이 `.730m` 이상에서만 켠다. 운반 검증과 보조 제어 이관은 기존
  `lift_streak=3`을 재사용해 현재도 3회 연속 안전 높이에 있어야 한다. 높이 복구 보상은 유지한다.
- sticky 들기 완료 뒤 행동자 소유·그립 유지·목표 `.17m` 안·높이 `.730m` 미만인 매초에 `-5`를
  부과한다. 60 control은 `-10`, 16초 자연 상한은 `-80`이다. 파지와 최초 들기에는 비용이 없다.
- 웹 ChatGPT Pro의 세 단계 검토에서 잘못 제안된 `.735/.715m` 히스테리시스와 단위가 맞지 않는
  `-.003/step` 비용은 반론 단계에서 폐기했다. 기존 `.730/.750m` 계약과 이진 경계를 유지했다.
- 파지·관측·자체 충돌·보조 제어·하강·놓기·PPO는 바꾸지 않았다. 전체 회귀 테스트 `146개`,
  Python 컴파일과 `git diff --check`를 통과했다.

```bash
python scripts/rsl_rl/train.py --task=Isaac-PickPlace-OpenArm-TestUSD-Bi-Stage-v0 --num_envs=5120 --headless --device=cuda --max_iterations=5000 --run_name=fresh_current_transport_clearance_v48
```

2500/3000/4000/4999회 최근 50회에서 sticky 완료 뒤 근접 저고도 주기/들기율이 매번 `<=5`,
운반/들기 `>=.98`, 파지·들기 목표 `>=90%`, 성공 최소 `>=55%`인지 확인한다. 마지막 GUI 20회는
바스켓 접촉 0회가 필수다. 마지막 하강, 접촉 주체 계측과 도메인 무작위화는 이번 수정에서 분리한다.
